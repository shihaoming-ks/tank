## 一、架构决策及其代价

### 1.1 服务端权威 + 客户端零判定

客户端只做两件事：**采集按键发意图**、**收快照画图**。不预测、不本地扣血、不本地判胜负。

这是「双端结果一致」这一门槛项唯一稳妥的路径。代价是操作有一个 RTT 的延迟感，
但在局域网/内网环境下不可感知，而任何客户端预测都会引入状态分叉的可能。

> ⚠️ 此约束在 S3~S6 全程有效。接素材、上基建都不得为了「看起来流畅」在客户端加判定。

### 1.2 `shared/` 是同一个物理文件，而非两份副本

```
server/ --import--> shared/constants.js <--import-- client/
                    shared/protocol.js
```

浏览器通过 `/shared/*.js` 静态路由拿到与 Node **完全相同**的文件。
协议常量天然只有一份，双端漂移在物理上不可能发生。

这比「用构建工具同步两份」更可靠：没有构建步骤，就没有「忘记重新构建」的失败模式。

### 1.3 网格 tilemap 而非任意矩形

碰撞退化为「算出实体覆盖哪几格，查数组」，O(4) 而非 O(n)。
更重要的是**避开了浮点缝隙穿墙**这一经典 bug ——
任意矩形做连续碰撞检测时，边界处的浮点误差极难彻底消除。

### 1.4 三类下行消息职责严格不重叠

| 类型 | 时机 | 语义 | 丢失后果 |
|---|---|---|---|
| `room` | 房间元数据变更 | 谁在房里、谁是房主、什么阶段 | 需重发，故仅在变更时下发 |
| `snapshot` | 30Hz | **幂等**的世界状态 | 无影响，下一帧自动纠正 |
| `event` | 事件发生时 | **一次性**瞬时信号，驱动特效与战报 | 特效丢失，但不影响状态 |

这个划分是刻意的：`snapshot` 幂等意味着丢帧无害，
而 `event` 只驱动表现层，即使丢失也不会导致双端状态不一致。

## 二、S1 各子阶段要点

### S1.1 端到端通路

先打通「浏览器能收到服务端回包」这一条最细的线，再往上堆功能。
Node 同时托管页面与 WebSocket，**同源**因此绕开跨域、混合内容、代理配置三类问题
（这些问题留到 S5 一次性面对）。

### S1.2 房间与玩家生命周期

**踩坑**：冒烟测试最初用「断言房间总数等于 N」，一旦有其他连接残留就整片失败。
改为**增量断言**（只检查自己关心的那几个 ID 的变化），从此不受外部干扰。

### S1.3 移动同步（技术风险归零点）

- tick 内用**真实 `dt`** 积分，不假设固定 33ms —— `setInterval` 必然漂移
- 碰撞失败**直接停住，不做滑动修正**：滑动在网格地图上会产生「贴墙自动转向」的诡异手感
- `input` 仅在按键状态**变化**时发送，而非每帧发，否则上行会被刷爆

### S1.4 战斗闭环

`endGame` 中广播顺序刻意为 **events → snapshot → over**：
先让特效与战报落地，再给最终状态，最后才是结算面板。
顺序颠倒会让玩家看到「先弹结算，再看到自己被击杀」的错乱时序。

**设计判断**：剩 1 名存活玩家判定为 **WIN 而非 aborted**。
虽然此时房间人数已不足开局要求，但对局是正常打完的，判为中止会让胜者失去胜利。

## 三、排查过的真实缺陷

这一节最有价值 —— 每条都是实际发生、有明确根因、并已加回归测试的问题。

### 3.1 ⭐「再来一局」要等很久才开始（`a57a097`）

**用户描述经历两次修正**，这个过程本身值得记录：

1. 「点击再来一局后没有反应」
2. 「不是没有反应，是等了很久才开始新的一局」
3. 「不是等待房主的问题，我就是在房主房间点击的」

我最初的假设（非房主点击被拒）**是错的**。前两次修正把我从错误方向拉了回来。

**根因**：`startGame()` 里有 `this.tick = 0`，而客户端有一行合理的乱序保护：

```javascript
if (state.snapshot && msg.t < state.snapshot.t) return;  // 丢弃乱序旧帧
```

第一局跑了 ~21 秒 ≈ 650 帧。新局帧号从 1 重新开始，于是**新局的前 650 帧全部被当作旧帧丢弃**。
画面冻结在上一局最后一帧，直到新局 tick 追上旧值才恢复 ——
**等待时长 ≈ 上一局的时长**。这解释了为什么「有时快有时慢」。

**修复**：`tick` 在房间生命周期内单调递增（永不重置），新增 `matchId` 标识局次，
快照携带 `m` 字段。客户端改为：

```javascript
const sameMatch = prev && (prev.m ?? 0) === (msg.m ?? 0);
if (sameMatch && msg.t < prev.t) return;   // 仅同一局内才比较帧号
```

**回归测试**：在 `smoke-combat.js` 中**复刻客户端的乱序丢弃逻辑**，断言 `dropped === 0`。
测真实行为而非实现细节，这样即使日后重构丢帧策略，测试依然有效。

**教训**：浏览器自动化曾报告耗时 6043ms，但我查服务端日志发现该房间只有**一次** `game_start`
—— 那次点击根本没启动对局（iframe 房间号混淆）。
**当自动化结果与日志矛盾时，相信日志。** 改用两个真实 WebSocket 连接实测，结果是 36ms。

### 3.2 错误提示被写进隐藏元素

`currentErrorEl()` 按当前视图挑选 `roomError` 或 `lobbyError`。
但结算面板属于 **game 视图**，于是 `NOT_HOST` 错误被写进了一个**当前隐藏**的元素 ——
表现为「点击毫无反应」，且极难定位。

**修复**：改为固定定位的全局 Toast。这从结构上消除了「错误写进隐藏元素」这一类缺陷，
而不只是修掉这一个实例。

### 3.3 相撞判定差一像素

`findTankCollisions` 容差原为 `TANK_SIZE + 2 = 28`。
实测出现 `dx=28` 的情形 —— `|dx| < 28` 恰好为假，漏检。

坦克按真实 `dt` 积分，停下位置是**连续值**，两车贴住时中心距落在 `TANK_SIZE ± 数像素`。
容差放宽到 `+5`。

**教训**：这类「差一像素」的边界不能按整数直觉设定。

### 3.4 钢砖比例剧烈波动（用户反馈「砖太多钢太少」）

表面看是均值不对，实际是**方差问题**：图块类型原先**按块**决定，
一个 2×2 块就占 4 格，样本太少导致钢块占比在 **10%~64%** 之间摇摆。

改为**逐格**决定类型后，30 局统计稳定在均值 45%。
顺带让同一块内混合两种材质，视觉上也更耐看。

### 3.5 测试中的隐含时序假设

- 障碍比例下调 → 地图变空旷 → 坦克跨越全图需约 5.3 秒，
  而「持续顶墙后坐标不再变化」只等了 1.6 秒 → 误报。
- 加入倒计时后一次性 25 项失败，全部因为测试在准备期就开始操作（**服务端行为是正确的**）。
  统一加 `waitCountdown()` 解决。

**教训**：参数一变就暴露的测试，说明它依赖了未声明的时序假设。

### 3.7 resumeToken 内存泄漏（长跑进程风险）

`resumeBindings` 这个 Map 有三处 `set`，却只在「token 校验失败」时 `delete` 一次。
玩家正常离开、房间销毁、观战者转正时旧 token 全都不清理 —— **只增不减**。

用最小脚本直接实例化 `RoomManager` 证实：

```
建并离开 5 个房间后：rooms=0  resumeBindings=5
再断开 5 个连接后：  rooms=0  resumeBindings=10
```

房间已全部销毁，却仍残留 10 条永不释放的记录。对需要长跑的服务端，
这等于「每个曾进过房的玩家都留一条永久痕迹」。

**修复**：token 生命周期集中由 `RoomManager` 管理，三个回收时机各自覆盖：

| 时机 | 方法 |
|---|---|
| 玩家真正离开 | `Room` 通过 `onPlayerGone` 回调通知 |
| 房间销毁 | `destroyRoom` 中 `revokeRoomTokens` |
| 观战者转正（重新签发） | `registerResumeToken` 内先作废旧的 |

用**回调**而非让 `Room` 直接持有 token 表：`Room` 不应知道 token 的存在，
否则鉴权逻辑会散落到两个类里。

**教训**：这类缺陷**不可能被冒烟测试发现** —— 功能全部正常，只是内存在涨。
只能靠直接断言容器大小。已加 `test/room-manager.test.js` 覆盖。

### 3.8 结算字段重复导致的潜在静默失效

`endGame` 的 `scores` 里 `spectator` 出现两次，且两行缩进异常。

当前**功能无害**（JS 重复键取后者，两处值相同），但这是定时炸弹：
一旦有人修改其中一处的取值逻辑，会得到一个静默失效的改动，极难排查。
已修正并加断言「每个字段只出现一次」。

### 3.9 ⭐ 测试的沉默失效（比报错更危险）

障碍比例降到 8% 后，`smoke-brick` 的断言数**从 14 掉到 4**，
但因为没有任何失败项，输出仍显示「失败 0」——
CI 看起来是绿的，实际上 10 个关键断言被静默跳过了。

根因：测试原本只检查出生点**正前方四向**有没有砖墙，没有就整段跳过。
地图变空旷后，这个条件经常不满足 —— 测试从「验证功能」退化成了「碰运气」。

**修复**：改用 BFS 主动**走到**能射击砖墙的位置，并把
「能找到可射击位置」本身变成一条**断言**而非跳过条件。
地图已保证有砖墙且全图连通，因此找不到就是真问题。

现在稳定 15/15（比原来还多一项「走位后瞄准方向仍有砖墙」）。

**教训**：带条件跳过的测试必须让「跳过」本身可观测。
只看「失败数为 0」会漏掉这类退化 —— **通过数的变化同样是信号**。

### 3.6 端口占用导致静默连错实例

`smoke:all` 曾静默连到一个残留的服务实例，而那个实例的地图模式与本组要求相反，
结果 114/128 且极难定位。现已加**端口占用即刻报错**。

## 四、玩法迭代（用户反馈驱动）

### 4.1 地图每局随机生成（`66e4290`）

三条硬约束保护随机性不失控：

1. **比例固定** —— 避免忽空旷忽拥挤
2. **出生点安全区** —— 不会开局即被围死
3. **BFS 连通性校验 + 重试** —— 随机生成完全可能把某个角围成孤岛，
   那样对局会直接失去意义（玩家永远碰不到面）。最多重试 30 次，
   全部失败则退化为「仅边界无障碍」—— **宁可地图单调，也不能让玩家进入走不通的图**。

图块区分 `BORDER`（边界）与 `BRICK`/`STEEL`（内部障碍），
为 S3 替换美术素材预留了语义区分。

### 4.2 六项玩法需求（`9372734`）

| # | 需求 | 实现要点 |
|---|---|---|
| 1 | 出生点每局随机但不过近 | 拒绝采样，间距 ≥240px；失败退化四角 |
| 2 | 开局 3-2-1 倒计时 | 新增 `PHASE.COUNTDOWN` |
| 3 | 障碍比例降低 | `MAP_FILL_RATIO` 0.18 → 0.11 → **0.08** |
| 4 | 砖墙 3 发可破 | 耐久编码进图块值 |
| 5 | 炮筒碰撞 | **反向解决**：缩小视觉而非扩大碰撞 |
| 6 | 相撞造成伤害 | 双向扣血 + 强制冷却 |

#### ⭐ 需求 5：为什么反过来做

用户自己提出了两个方向：「计算炮筒碰撞」或「缩小坦克主体使 AABB 对应一个网格」。
我选了后者，因为给炮筒加碰撞有两个难以接受的后果：

1. **贴墙时无法转向** —— 炮筒扫过墙面即被阻挡，坦克贴墙后方向就锁死了。
   而贴墙调整射击角度是坦克类游戏的基本操作。
2. **碰撞盒变成方向相关的非正方形** —— 网格查表 O(4) 的优势尽失，
   且转向瞬间可能直接嵌入墙体，需要额外的「转向合法性」判定。

于是让视觉服从碰撞：`TANK_SIZE` 24→26，新增 `TANK_BODY=18` 与 `BARREL_LEN=4`，

```
车体 18 + 炮筒 4×2 = 26 = 碰撞盒     ← 视觉永不超出碰撞盒
26 < TILE(32)                        ← 仍可穿过单格通道
```

代价最小、手感最好。

#### 需求 2：倒计时的三个细节

- `startedAt` 指向**倒计时结束时刻**，使对局时限与无敌期都不包含准备期
- 移动与开火天然被 `phase !== PLAYING` 拦下，**无需新增分支**
- 倒计时结束时**清空 `moveDir`** —— 否则提前按住方向键的玩家会抢跑

#### 需求 4：耐久编码进图块值

`BRICK`(3) / `BRICK_2`(2) / `BRICK_1`(1) 三个图块值表示剩余耐久。
好处是**地图始终是纯数字二维数组** —— 快照序列化与客户端渲染都无需为耐久新增数据结构。

地图变更走**增量下发**（快照 `mp` 字段）。地图约 600B，全量重发在 30Hz 下会让流量翻十倍。

#### 需求 6：冷却是必需的

两车贴住时**每帧都重叠**，无冷却会在 30Hz 下一秒内扣光双方全部血量。故设 1200ms 冷却。

另两条规则：
- **双方同时扣血**，撞人者不占便宜 —— 否则会演变成「互相撞死」的下水道玩法
- **相撞致死不计对方击杀数** —— 计入会鼓励自杀式撞击

### 4.4 P2 道具系统与坦克升级

新增功能：

| 功能 | 说明 |
|---|---|
| 道具系统 | 每 20s 刷新，场上最多同时存在 2 个；击碎砖块 25% 概率掉落 |
| 护盾 🛡 | 持续 1.5s，免疫伤害 |
| 加速 ⚡ | 持续 3s，移速 ×2 |
| 强化弹 🔥 | 持续 5s，子弹体积 +4px、伤害 +1 |
| 血包 ❤️ | 即时回血 **1 点**（不超上限） |
| 复活甲 ✨ | 概率约 7%（权重 1/14），触发后半血复活 + 无敌期，而非真正被击杀 |
| 坦克升级 | 累计击杀 ≥2 自动晋级，子弹体积 +4px、伤害 +1，金色脉冲外框提示 |

**权重随机**：护盾/加速/强化弹各权重 3，血包 4，复活甲 1。
**道具频率设计**：主动刷新间隔长（20s），主要获取途径是「打砖块换道具」（25% 掉落），鼓励进攻而非蹲点等刷。

### 4.5 Safari 输入框修复

原方案（多格独立 `<input>`）在 Safari 上有两个根本性问题：
1. `focus()` 同步调用 → Safari 将当前按键事件路由到新焦点，导致「填两格」
2. 移动端 `e.key = "Unidentified"` → keydown 拦截失效；`maxlength=1` 阻止追加 → 覆盖无效

最终方案：**单个透明 input（opacity:0）+ 4 个视觉 `.otp-cell`**。
- 真实 input 永远不跳焦，从根本上消除 Safari 多格路由问题
- 4 个格子纯视觉，由 JS 读取 `input.value` 同步文字与高亮
- 点击格子：按 X 坐标除以容器宽算出格子索引，`setSelectionRange` 定位光标
- 输入时：`keydown` 检测到光标为插入点（无选区）且在已有字符内，提前 `setSelectionRange(s, s+1)` 选中该字符，使字符输入自动变「替换」而非「插入」

| 反馈 | 处理 |
|---|---|
| 3-2-1 后应有「开始」提示 | 画布中央绿色「开始！」放大淡出，与琥珀色读秒形成色彩区分 |
| 「再来一局」的顶部 Toast 多余 | 移除。已有倒计时与「开始！」两重提示，再叠浮层反而干扰视线 |
| 整体障碍还是偏多 | `MAP_FILL_RATIO` → 0.08（均值 8.3%，波动仅 1.2%）|
| 砖太多、钢太少 | 见 §3.4，实为方差问题 |
| **血量太小不明显** | 见下方 |

**血量可见性**的关键一改是**在坦克头顶绘制血条**：
对战时视线锁在战场，看顶部 HUD 需要移开目光，
而血量恰恰是最高频、最需要即时感知的信息。

HUD 同时从 `❤❤❤` 字符改为分段方块 —— 字符笔画细且受字体渲染影响大，
方块能在余光里一眼数清；空槽保留描边，这样能看出「总共几格、还剩几格」。
自己那条更大；1 血时两处同时转红并脉动。

### `TANK_EMPTY_MAP=1` 测试钩子

战斗冒烟要验证的是「射击 → 命中 → 淘汰 → 结算」这条链路，**而非寻路能力**。
随机掩体会迫使测试脚本实现 AI 寻路才能打中对手 —— 既脆弱又与被测目标无关。
（我确实尝试过贪心与 BFS 寻路，20 秒只推进了 670px。）

于是加了环境变量钩子生成空旷地图。**地图随机性本身由 `test/map.test.js` 以 50 个种子独立覆盖，不会漏测。**

砖墙测试与战斗测试的地图要求**互斥**，故 `smoke-brick.js` 独立成文件 ——
合在一处必然有一方被跳过。

### 一次有价值的诊断方法

战斗测试在随机地图下失败时，我用**纯函数直接验证**而非猜测：
射手 x=309、目标 x=366、同一行、相距 57px，但射手右边缘 321 已落在第 10 列，
而那一列有砖墙。移除该砖墙后立即命中 —— **证明物理层完全正确，是测试假设有问题**。

`physics.js` 写成纯函数的价值正在于此：可以零 mock 直接调用来定位问题。

## 七、环境相关注意事项

开发过程中踩到的工具限制，记录以免重复踩：

| 现象 | 应对 |
|---|---|
| `browser_click`/`browser_press_key` 不可用 | 用 `browser_evaluate` 传函数体 `() => {...}`，**不是** IIFE |
| `location.reload()` 后首次 evaluate 抛「Execution context was destroyed」 | 重试一次 |
| 只有一个可控标签页 | 第二名玩家用同源 iframe（⚠️ iframe 的房间号状态可能误导，见 §3.1）|
| 单次 `browser_evaluate` 过长会失败 | 拆成多个小调用 |
| `node --test test/` 把目录当模块 | 用 `node --test test/*.test.js` |
